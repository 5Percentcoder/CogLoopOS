# 受控缩写扩展能否改善技术语料检索

## 1. 触发问题

企业 AI 技术文档经常混用 `RAG`、`MCP` 等缩写和英文全称。只依赖词法重合时，
查询可能命中包含同名缩写的无关文档，而漏掉只写全称的正确文档。

这条闭环验证：在进入更昂贵的 embedding、reranker 或 GraphRAG 方案前，
一个小型、可审核的缩写扩展表是否值得作为检索预处理候选。

## 2. 当前理解

- **Fact：** 词法检索只能利用查询与文档中实际出现的词项。
- **Fact：** `RAG`、`MCP` 在不同领域可能具有不同含义。
- **Unknown：** 保留原查询并添加受控全称，能否提升当前测试集的 Recall@1，
  同时不损害不需要扩展的查询。

## 3. 可证伪假设

- **Hypothesis：** 对缩写与全称不一致的技术查询，受控查询扩展会让整体
  Recall@1 相对基线至少提高 25 个百分点，并且不降低非扩展查询子集的 Recall@1。
- **如果假设错误，应观察到：** 整体提升不足 25 个百分点，或非扩展查询子集
  出现任何下降。

## 4. 实验契约

- **主要指标：** 全部查询的 Recall@1。
- **通过阈值：** 相对基线至少提升 `0.25`。
- **护栏指标：** 非扩展查询子集 Recall@1 不下降。
- **固定变量：** 文档、查询、分词、评分和并列排序策略；实验组只增加白名单扩展词。
- **最小数据集：** 8 篇人工可审查文档、6 个查询；其中 2 个缩写歧义查询，
  4 个无需扩展的技术查询。
- **运行命令：**

```bash
python3 experiments/2026-07-09-controlled-query-expansion/evaluate.py
```

## 5. 证据

- **Observation：** 基线 Recall@1 为 `0.6667`，扩展后为 `1.0000`，
  提升 `0.3333`。
- **Observation：** 非扩展查询子集在两组中均为 `1.0000`，没有下降。
- **Observation：** 两个缩写查询由错误命中同名缩写文档，变为命中包含目标技术全称的文档。
- **原始结果：** `experiments/2026-07-09-controlled-query-expansion/result.json`
- **可复现性：** 实验仅使用 Python 标准库；脚本固定数据与排序规则。

## 6. 工程判断

- **Decision：** 将“原查询 + 高置信度白名单全称”保留为企业 RAG 查询预处理的
  候选策略，并在真实评估集上与无扩展基线做 A/B 对比。
- **适用范围：** 领域缩写稳定、有审核词表、文档可能只写全称的语料。
- **不适用范围：** 开放领域、缩写高度歧义、词义依赖上下文且无法可靠消歧的查询。
- **风险与限制：** 此结果来自刻意构造的小数据集，只证明机制和学习闭环可运行，
  不证明生产收益；词表膨胀还可能降低 Precision@k。
- **需要生产数据验证的部分：** Recall@k、MRR、nDCG、端到端答案正确率、
  延迟、误扩展率和人工判定的失败类型。
